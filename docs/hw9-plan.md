# ДЗ 9. План выполнения

## Условия и исходное состояние

Тема: основы многопоточности в Go. Срок в заголовке задания: 16.11.2026. Первичные условия: три PNG из соседнего каталога `Домашнее задание 9. Дедлайн 16.11.2026`, снимки 14.11.2026 в 14:15:41, 14:15:47 и 14:15:51. Работа продолжает ДЗ 8 в `go-homework`, исходный тег `hw8`.

В Gateway уже есть `GET /api/reports/summary`, а Ledger считает отчет одним SQL-запросом и кеширует суммы в Redis. Все методы сервиса принимают контекст, SQL использует контекстные вызовы. Нужно изменить существующий расчет и добавить общий HTTP-таймаут, сохранив архитектуру и прежние результаты.

| Требование | Решение | Проверка |
| --- | --- | --- |
| Middleware с `context.WithTimeout` | 2 секунды по умолчанию, настройка флагом Gateway; контекст передается всем обработчикам | Все API-маршруты, отмена родителя, короткий таймаут |
| Единая ошибка отмены | 504 и `{"error":"request timed out"}` для отмены и дедлайна | Ответы всех методов и отсутствие подмены обычных ошибок |
| Отчет по датам | Сохранить существующий маршрут, разбор дат и JSON с `from`, `to`, `categories`, `total` | Старые HTTP-тесты и curl |
| Параллельные суммы | Список категорий с расходами в диапазоне, отдельная горутина на каждую, `sync.WaitGroup` | Барьер в тесте доказывает одновременный запуск |
| Нет гонок | Каждая горутина пишет только в свой элемент результата/ошибок, объединение после `Wait` | `go test -race`, стабильный порядок категорий |
| Быстрая отмена | Один дочерний контекст для расчета, отмена остальных работ при ошибке, ожидание всех горутин до возврата | Ошибка одной категории, дедлайн, отмена клиента, блокировка SQL |
| Heartbeat | Фоновая горутина с `time.Ticker` раз в 400 мс; остановка тикера и ожидание горутины при любом выходе | Длительный расчет, успешное завершение и отмена; отсутствие сообщений после возврата |
| Контекст через слои | Контекстные SQL-запросы и Redis, отмена операций в памяти; HTTP-слой не обращается к БД | Проверка импортов, тесты репозиториев и живого сервера |
| Документация и сдача | README с примером отчета, настройкой таймаута и воспроизводимой проверкой отмены | Самопроверка, независимое ревью, `main` и тег `hw9` |

## Решения после проверки плана

1. Не создавать второй маршрут и второй алгоритм отчета. Заменить репозиторный расчет всего отчета выборкой категорий и существующей суммой по категории. Оркестрация остается в сервисе.
2. Сохранить кеш отчетов на 30 секунд, его ключи и полезную нагрузку из ДЗ 7. Кеш подключается к сервису через небольшой контракт чтения/записи сумм; при попадании горутины расчета не нужны. При промахе используется новый параллельный расчет. Кеш бюджетов и бюджетное правило не меняются.
3. Сохранить включение обоих граничных дней: сервис переводит конец отчета в начало следующего календарного дня для существующей суммы по полуоткрытому диапазону. Не прибавлять 24 часа, чтобы не нарушить переходы часовых поясов.
4. Список категорий содержит только категории с расходами в запрошенном диапазоне, сортировка по байтам сохраняется. Независимые SQL-запросы видят состояние на момент каждого запроса; общий снимок при конкурентной записи условием не требуется. Итоговая сумма всегда складывается из возвращенных сумм категорий.
5. После первой ошибки отменить соседние вычисления, дождаться их выхода и вернуть причину отказа, сохранив `errors.Is`. Не отдавать частичный отчет и не записывать его в кеш.
6. Таймаут кооперативный: обработчики и сервис завершают работу по контексту, middleware не оставляет отдельную горутину HTTP-обработчика. Для чтения тела запроса ограничить сетевой дедлайн; ошибки чтения по таймауту тоже возвращают 504. Не менять 400 для обычного неверного JSON и дат.
7. Для демонстрации отмены использовать маленький таймаут и контролируемую блокировку тестовой БД. Не добавлять задержки, отладочные эндпоинты и переключатели в рабочую бизнес-логику. Проверять промах кеша, чтобы попадание не скрыло расчет.
8. Сохранить Go 1.22 и существующие библиотеки. Для кода применять `go-readability`. Проверки запускать на отдельном временном стенде, пользовательские данные не затрагивать.

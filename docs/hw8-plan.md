# ДЗ 8. План выполнения

## Условия и границы

Тема: архитектура и дизайн приложений. Исходные условия: три снимка экрана в соседнем каталоге `Домашнее задание 8. Дедлайн 10.11.2026`, сделанные 14.11.2026 в 14:14:37, 14:14:42 и 14:14:59. В заголовке указан срок 10.11.2026, в общем тексте указан срок 7 дней после вебинара. Работа выполняется в `go-homework`, поверх ДЗ 7.

Задача: выделить доменные сущности и контракты хранения, перенести бизнес-логику в сервис, внедрить зависимости через конструкторы и убрать из Gateway знание об устройстве хранилища. Сохранить HTTP-контракт, PostgreSQL, Redis, консольное демо и проверки предыдущих заданий.

| Требование | Реализация и критерий проверки |
| --- | --- |
| Доменные сущности и валидация | `ledger/domain`: транзакции, бюджеты, периоды, ошибки, отчеты и интерфейсы репозиториев. Нет SQL, HTTP и импортов внешних слоев. |
| Контракты хранения | Сохранение бюджетов, поиск бюджета по категории, списки бюджетов и расходов, добавление расхода, сумма расходов категории за диапазон, агрегаты отчета. |
| PostgreSQL | `ledger/internal/repository/pg`: ранее подготовленные SQL-запросы, реализация доменных контрактов, без проверки бизнес-лимита. |
| Сервис | `ledger/service`: интерфейс приложения и реализация. Валидация, нормализация, выбор периода, проверка бюджета и расчет отчета. Зависит только от доменных контрактов и стандартной библиотеки. |
| Фабрика | Пакет `ledger`: `New(ctx)` возвращает интерфейс сервиса, функцию закрытия и ошибку. Читает конфигурацию, открывает подключения, проверяет таблицы и собирает зависимости. Не запускает миграции. |
| Gateway | Получает сервис из фабрики и передает в `api.NewRouter(service)`. Обработчики вызывают его методы с контекстом запроса. DTO и отображение ошибок остаются в HTTP-слое. |
| Регрессия | Тесты ДЗ 6-7, race detector, vet, интеграционные проверки PostgreSQL/Redis и HTTP-сценарии ДЗ 5. |
| Документация | README описывает слои, направление зависимостей, создание сервиса и команды запуска/проверки. |

## Архитектурные решения

1. Сохранить отдельные Go-модули `hw1`, `gateway`, `ledger`, Go 1.22 и существующие зависимости. Общие для Gateway типы и интерфейс сервиса разместить в публичных пакетах `domain` и `service`: Gateway не может импортировать `ledger/internal/*`.
2. Удалить изменяемое пакетное хранилище. Каждый вызов фабрики создает самостоятельный сервис. Для демо и тестов использовать отдельную фабрику сервиса с хранилищем в памяти.
3. Сохранить атомарность проверки бюджета и вставки расхода. Доменный контракт выполнения операции передает сервису репозитории, связанные одной транзакцией. Сервис читает бюджет, вычисляет сумму и проверяет лимит внутри этой операции. PostgreSQL удерживает блокировку строки бюджета до завершения записи; хранилище в памяти удерживает mutex. Ошибка и паника освобождают ресурсы и не оставляют частичной записи.
4. Загрузка нескольких бюджетов сохраняет атомарность и единый порядок захвата блокировок по категории. Пустой период по-прежнему означает лимит за все время. Суммы округляются до копеек, даты и периоды считаются в локальном часовом поясе.
5. Сохранить кеш отчетов и списка бюджетов из ДЗ 7 как обертку репозиториев. Бюджет при добавлении расхода читается непосредственно из основного хранилища. Отчеты могут отставать на TTL, изменение бюджетов сбрасывает кеш списка, отказ Redis после запуска приводит к чтению из PostgreSQL.
6. Все операции сервиса принимают `context.Context`; существующий таймаут ограничивает запрос, сохраняя отмену родительского контекста. Фабрика передает полученный контекст в стартовые проверки подключений и закрывает уже открытые ресурсы при ошибке.
7. HTTP-слой разбирает JSON и строковые даты, а сервис проверяет доменные значения. Ошибки валидации преобразуются в 400, превышение бюджета в 409, ошибки хранения в прежний ответ 500. Структуры JSON, 201, 404, 405, `Allow`, `Content-Type` и пустые массивы сохраняются.

## Порядок выполнения

1. Зафиксировать исходное состояние Git и результаты существующих тестов. Проверить потребителей пакетных функций, внутренние тестовые обращения к хранилищу, консольный запуск и поведение Redis.
2. Выделить доменные типы, ошибки, методы валидации, календарные операции и минимальные контракты репозиториев. Не переносить в домен подключения и глобальное состояние.
3. Реализовать репозитории PostgreSQL и памяти. Сохранить сортировку, копирование результатов, SQL-агрегации, атомарную загрузку бюджетов и блокировки. Проверку превышения бюджета убрать из хранилищ.
4. Реализовать сервис через внедрение репозиториев. Перенести в него нормализацию, загрузку JSON-бюджетов, бюджетное правило и вычисление отчета. Проверить ошибки каждого этапа и отсутствие записи после отказа.
5. Подключить существующий Redis через обертку репозиториев, собрать фабрики постоянного и временного сервиса. Проверить успешное закрытие, повторное закрытие, ошибку старта, отмененный контекст и отсутствие таблиц без автоматического запуска миграций.
6. Перевести Gateway и консольную программу на экземпляры сервиса. Передать зависимости через конструкторы/аргументы, убрать пакетные вызовы CRUD и доступ HTTP-слоя к хранилищам.
7. Адаптировать прежние тесты к экземплярам сервиса без ослабления проверок. Добавить проверки независимости сервисов, отмены контекста, порядка операций и ошибок репозиториев. Проверить сервис с подменяемыми доменными зависимостями, Gateway с подменяемым сервисом.
8. Запустить `gofmt`, `go test -race ./...`, `go vet ./...` в каждом модуле. Проверить совместимость с Go 1.22. На отдельном временном стенде запустить PostgreSQL/Redis, применить существующие миграции отдельной командой и выполнить интеграционные тесты и curl-сценарии.
9. Обновить README, проверить импорты, итоговый diff и соответствие каждому пункту задания. Исправить обнаруженные ошибки и повторить затронутые проверки.
10. Подготовить и проверить отдельный Markdown-промпт для независимого ревью: исходные условия, границы, файлы, команды, контракт API, риски и формат замечаний. Создать отдельный чат проекта, передать промпт, дождаться результата. Проверить замечания, исправить подтвержденные проблемы и повторить необходимые проверки.
11. Зафиксировать готовое решение локальным коммитом. Публикация и изменение видимости требуют отдельной явной команды согласно `../AGENTS.md`. После публикации проверить доступность ссылки и отметить состояние сдачи тегом `hw8`, не перемещая существующие теги.
